# ADR-0004. Збереження, відновлення і їхня видимість

**Статус:** реалізовано (PR #15, #28, #41, #42). **Дата:** 2026-09-27.

## Контекст

- Операторські бани жили лише в пам'яті й тихо зникали після рестарту.
- Пізніше запис став надійним, але tick чекав диска без дедлайну. Повільний диск зупиняв
  expiry і heartbeat, а здоров'я лишалося «ok» (R27-03).
- Пошкоджений файл стану виглядав як перший старт (R27-04).

## Рішення

- **Що зберігається** (`--state-file`): власні заявки вузла, зняття оператора, власні
  відкликання, кінці lease пірів (ADR-0003) і пам'ять подій детектора (ADR-0009). Заявки
  пірів повертаються через меш.
- **Як пишеться.** Файлом володіє **окремий потік запису**. Tick лише передає знімок із номером
  покоління й ніколи не чекає диска.
  - Передача має один замінний знімок і один сигнал пробудження. Нові передачі
    замінюють очікуваний знімок навіть під час завислого запису. Окремо потік тримає
    один знімок, який пишеться або чекає повтору після помилки; новіший замінює невдалий.
  - StateStore спарює покоління й знімок під своїм mutex. У власника таблиці
    `submit_state` тримає mutex BlockTable від `take_persisted` (який очищає dirty)
    до синхронного `submit`. Тому порядок захоплення таблиці збігається з порядком
    передачі: старіший знімок не отримує новіше покоління, а clean caller не
    підтверджує ще не переданий стан. Сирий API StateStore впорядковує лише `submit`.
  - Файлові операції writer і очікування `wait_durable` виконуються поза mutex таблиці.
    Критична секція містить захоплення й передачу знімка, включно зі звільненням
    заміненого знімка; це не межа часу чи wait-free гарантія.
  - Межа стосується кількості утриманих знімків, не RSS чи розміру одного знімка,
    буферів JSON і пам'яті caller. Передача не чекає диска, але не є wait-free.
  - Старіше покоління ніколи не перезаписує новіше. Підтвердження durable з'являється
    тільки після успішного запису, не після передачі чи заміни знімка.
  - Невдалий запис повторюється. Скасування завислого filesystem syscall немає;
    без його повернення жодне наступне покоління не стає durable.
  - Сам запис: тимчасовий файл → `fsync` → `rename` → `fsync` каталогу, права `0600`.
- **Що обіцяно.**
  - **Рішення оператора** чекають, поки їхнє покоління потрапить на диск, але не довше 2 с.
    Далі відповідь `OK …; WARNING: not yet durable …` каже, що результат запису ще невідомий;
    у ядрі рішення вже діє.
  - **Рішення детектора** (`OK applied`) потрапляють на диск протягом одного тіку плюс час
    запису. Крах раніше губить їх локально: детектори повторюють, піри повертають свої заявки.
  - **Штатне завершення** чекає фінального запису не довше 5 с.
- **Відновлення** розрізняє три випадки:
  - файлу немає → перший старт;
  - файл відновлено → відновлені заявки заново перевіряються політикою «ніколи не блокувати»;
  - провал: файл нечитабельний або не розбирається. Його байти зберігаються під першим вільним
    `*.corrupt[.N]`, наявну копію не перезаписує жодна. Вузол лишається DEGRADED, доки
    оператор не надішле `ACCEPT_STATE_LOSS`. Локальний захист працює й далі.

## Розглянуті варіанти

- **Лише пам'ять.** Бан тихо зникав.
- **Tick чекає запису.** Повільний диск зупиняв expiry.
- **Скасовувати завислий запис.** Системний виклик не скасовується, і порядок записів
  втрачається.
- **Не стартувати з пошкодженим станом.** Відбирає локальний захист через зіпсований файл.
- **Тихо почати з нуля.** Втрачені зняття дозволили б ресинхронізації повернути знятий блок.

## Наслідки

- Метрики `sokol_state_healthy`, `sokol_state_pending_seconds` (вік найстарішої незбереженої
  зміни) і `sokol_state_restore_ok`. Заміна очікуваного знімка зберігає час першої
  передачі в цій черзі. Завершення старішого запису не поновлює grace period
  для вже старої черги; оновлення її віку серіалізоване з `submit`.
- Файл стану несе номер схеми (`schema`, зараз 1). Файл іншої схеми відхиляється з
  назвою обох версій (провал, байти збережено), а не як «пошкоджений». Міграцій немає, доки
  немає релізу. Файл без номера (до появи поля) читається як схема 1.

## Перевірка

- Модуль `state_store`: `a_hung_disk_neither_blocks_callers_nor_looks_healthy`,
  `a_failing_disk_is_retried_and_reported`, `restore_tells_fresh_corrupt_and_unreadable_apart`,
  `a_failed_restore_keeps_the_node_degraded_until_the_loss_is_accepted`.
- Обмежена передача й відновлення: `a_hung_writer_retains_only_the_latest_handoff_and_recovers_it`,
  `concurrent_submitters_preserve_the_latest_generation_and_snapshot_pair`,
  `finishing_an_older_write_does_not_refresh_pending_health`,
  `a_failed_write_is_replaced_by_the_newest_queued_snapshot`.
- Порядок власника таблиці: `a_newer_operator_snapshot_cannot_be_overwritten_by_an_older_capture`
  і `a_clean_caller_cannot_acknowledge_an_unsubmitted_capture` у `main::tests::persistence`.
  Контрольований порядок потоків на звільненні справжнього Tokio mutex відтворює
  захоплення → новіший caller → запізніла передача. Працюють справжні
  `submit_state`, `persist_now`, BlockTable, StateStore і файловий запис;
  kernel map замінена тестовим драйвером. Callback запису відкривається лише після
  першої спроби `persist_now`, тож пропущене очікування не дає хибного успіху.
- Smoke наживо:
  - бан переживає рестарт і SIGKILL одразу після `OK`;
  - FIFO замість тимчасового файлу, тобто завислий диск: відповідь < 4 с із попередженням,
    tick працює далі, вузол у DEGRADED; наступні ban/unban діють без durable-підтвердження,
    після звільнення диска файл містить новий ban і здоров'я повертається;
    після SIGKILL і рестарту з цього файла новий ban і попереднє unban залишаються чинними;
  - пошкоджений файл стану → DEGRADED, байти збережено, `ACCEPT_STATE_LOSS` знімає DEGRADED.

## Коли переглянути

Коли знадобиться міграція схеми стану, журнал замість знімків (великі обсяги пам'яті подій)
або підписані операторські рішення.
