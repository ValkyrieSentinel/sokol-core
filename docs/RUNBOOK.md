# Runbook оператора

Для людини, що встановлює й обслуговує вузол Sokol-Core, без автора поруч. Кожна команда тут
перевіряється в `scripts/xdp-smoke.sh` або береться з `deploy/`. Де поведінку не перевірено, це
сказано. Шляхи — як у `deploy/sokol-orchestrator.service`.

Весь шлях від встановлення до пакета для підтримки проганяє `scripts/runbook-rehearsal.sh` на
чистому systemd-хості (див. кінець документа).

Перевірені середовища — у [SUPPORT.md](SUPPORT.md). Чому система поводиться саме так — у
[ARCHITECTURE.md](../ARCHITECTURE.md) і [ADR](adr/README.md).

Скорочення для керуючого сокета (усі команди нижче):

```shell
ctl() { printf '%s\n' "$1" | sudo nc -U -q1 /run/sokol/control.sock; }
metric() { curl -s http://127.0.0.1:9469/metrics | grep "^$1"; }
```

## 1. Встановлення

```shell
cd ebpf && cargo build --release --locked && cd ..
cargo build --release --locked
sudo useradd --system --no-create-home --shell /usr/sbin/nologin sokol
sudo groupadd --system sokol-ipc     # детектори: IPC-сокет
sudo groupadd --system sokol-ops     # оператори й дашборд: керуючий сокет
sudo install -m 0755 target/release/orchestrator /usr/local/bin/sokol-orchestrator
sudo install -m 0755 target/release/monitor /usr/local/bin/sokol-monitor
sudo install -m 0644 deploy/sokol-orchestrator.service /etc/systemd/system/
sudo install -d -o sokol -g sokol -m 0700 /var/lib/sokol   # як StateDirectory; потрібен уже в §2
sudo install -d -m 0755 /etc/sokol
```

`/etc/default/sokol`:

```shell
SOKOL_ARGS=--interface eth0 --node-id 1 --peers-file /etc/sokol/peers.json \
  --seed-peer 10.0.0.2:7946 --metrics-bind 127.0.0.1:9469 \
  --never-block 203.0.113.0/24
```

- `--node-id` унікальний у меші.
- `--never-block` — мережі операторів і бастіонів; адреси самого вузла, його шлюзи,
  seed-піри й endpoint'и WireGuard-пірів захищені й так.
- Метрики вмикаються лише з `--metrics-bind`.
- Синхронізація часу (chrony або NTP) обов'язкова.

## 2. Ключі й піри

```shell
sudo -u sokol /usr/local/bin/sokol-orchestrator --key-file /var/lib/sokol/node.key --print-public-key
```

Виводить `mldsa65:<hex>`; файл ключа створюється при першому запуску (`0600`). Зберіть ключі
всіх вузлів у `/etc/sokol/peers.json` на **кожному** вузлі (меш має бути повним). Файл
потрібен до старту служби; перший вузол, поки інших немає, стартує з `[]`.

```json
[
  { "node_id": 2, "public_key": "mldsa65:<hex вузла 2>" },
  { "node_id": 3, "public_key": "mldsa65:<hex вузла 3>" }
]
```

## 3. Перший старт і перевірка

```shell
sudo systemctl enable --now sokol-orchestrator
journalctl -u sokol-orchestrator -n 50 --no-pager
```

| Що перевірити | Як | Очікується |
|---|---|---|
| Версія й збірка | `metric sokol_build_info` | `version=…,build=<commit>` |
| Здоров'я вузла | `sokol_audit_healthy`, `sokol_state_healthy`, `sokol_state_restore_ok`, `sokol_protected_refresh_ok`; дашборд показує `MODE` з heartbeat | усі чотири присутні й `1`, `MODE=NORMAL`; FlowSpec перевіряється окремо за §5.7 |
| XDP на інтерфейсі | `ip -d link show eth0` | `prog/xdp` |
| Піри з'єднані | `metric sokol_p2p_active_peers` | кількість інших вузлів |
| Бани оператора | `ctl LIST_BANS` | `OK <n> …` |
| Ланцюжок аудиту | `sudo sokol-monitor --verify /var/lib/sokol/audit.log` | `OK …` |
| Захищені адреси читаються | `metric sokol_protected_refresh_ok` | `1` |

Код виходу `sokol-monitor --verify`: `0` / `OK` — перевірено збережений ланцюжок;
`1` / `BROKEN` — виявлено порушення; `2` / `UNVERIFIED` — перевірка недоступна
(каталог, файл, читання чи metadata). Для автоматизації звіряйте і код, і verdict;
I/O-помилка не доводить пошкодження. `OK` не підтверджує повноти історії:
неповний хвіст активного файлу допускається, старі сегменти могли бути видалені
за retention policy (AUDIT-V1). Під час живої ротації `BROKEN` може означати
несумісний набір сегментів, побачений між двома операціями читання. Перед
висновком про підміну повторіть перевірку на стабільному наборі файлів:
ця команда не створює атомарного snapshot.

## 4. Метрики, за якими стежити

| Метрика | Тривога, якщо | Значення |
|---|---|---|
| `sokol_audit_healthy` | `0` | аудит не пишеться (диск, права); захист працює (ADR-0005) |
| `sokol_state_healthy` | `0` | файл стану не пишеться або зміна чекає > 5 с (ADR-0004) |
| `sokol_state_pending_seconds` | росте | диск повільний або завис |
| `sokol_state_restore_ok` | `0` | стан при старті не відновився, див. §5.4 |
| `sokol_protected_refresh_ok` | `0` | адреси хоста не читаються; захищено останні відомі |
| `sokol_blocks_pending` / `…_oldest_seconds` | > 0 довго | карта ядра не приймає записи (переповнена) |
| `sokol_blocks_active` vs `sokol_blocks_capacity` | > 80 % | наближається ліміт 65 536 |
| `sokol_p2p_active_peers` | менше очікуваного | див. §5.5 |
| `sokol_mesh_envelopes_rejected_total{reason="stale_timestamp"}` | росте | годинник піра й цього вузла розійшлися понад 30 с (NTP) |
| `sokol_clock_steps_total` | зросла | годинник вузла крокував на `sokol_clock_last_step_seconds`. Чинні блоки зберігають тривалість (ADR-0017), але якщо годинник тепер розходиться з пірами понад 30 с, вузол випадає з мешу (див. `stale_timestamp`) |
| `sokol_claims_waiting` | > 0 довго | пір видав більше рішень, ніж дозволяє його конверт (`--peer-max-active`, 16 384, ADR-0007): решта чекає на слот. Через це кількість блоків на вузлах різниться, хоча меш справний |
| `sokol_mesh_broadcasts_dropped_total{class="urgent"}` | росте | лінк до піра не встигає за заявками |
| `sokol_mesh_handshake_timeouts_total` | швидко росте | хтось відкриває з'єднання й мовчить |
| `sokol_tick_seconds_max` | > 0,5 | обслуговування таблиці сповільнюється |
| `sokol_xdp_events_lost_total` | росте | orchestrator не встигає читати події ядра: кільце повне, події (не блоки) губляться |
| `sokol_xdp_events_malformed_total` | > 0 | XDP-програма й orchestrator розходяться в розкладці подій (ADR-0015): бінарник зібрано неправильно |
| `sokol_block_outcomes_total{effect="none"}` | частка велика | блоки нічого не відкидають: `sudo sokol-monitor --outcomes /var/lib/sokol/audit.log` покаже, які детектори й правила (ADR-0014) |

Будь-яка з перших п'яти причин переводить вузол у `MODE=DEGRADED`. Захист при цьому працює.

**Готові алерти й дашборд:**
- `deploy/prometheus/sokol-alerts.yml` — 16 правил за цією таблицею, з тестами
  `promtool test rules sokol-alerts.test.yml`;
- `deploy/prometheus/prometheus.yml` — приклад збору. Метрики без автентифікації, тож
  `--metrics-bind` лише на приватну адресу (WireGuard, мережа керування);
- `deploy/grafana/sokol-dashboard.json` — імпорт у Grafana. Ряди: стан вузлів, фаза 0
  («відкинув би»), рішення й наслідки, меш, ресурси.

## 5. Інциденти

### 5.1 Помилковий блок

```shell
ctl "UNBAN_IP:198.51.100.7"       # знімає всі відомі рішення про ціль, і для пірів теж, локально
ctl FLUSH_BANS                    # усі динамічні блоки (детектори, меш); бани оператора лишаються
ctl FLUSH_ALL                     # і бани оператора; --block лишається
```

- Власні рішення детектора знімаються на всьому меші; чужі — лише на цьому вузлі.
- Нове виявлення тієї самої адреси — нове рішення, і воно заблокує знову.
- Що зробив знятий блок, видно в аудиті: `BLOCK_OUTCOME|IP:…|Dropped:…|Seconds:…`.
- Щоб адреса не блокувалась ніколи, додайте її в `--never-block` і перезапустіть службу.

### 5.2 Вузол заблокував би себе чи шлюз

Політика цього не дозволяє: адреси вузла й шлюзи перечитуються кожні 2 с (ADR-0012). Блок
адреси, що щойно стала своєю, знімається протягом 2 с (`BLOCK_RELEASED_PROTECTED` в аудиті).
Зовнішні адреси WireGuard-пірів захищаються автоматично (потрібен інструмент `wg`); адреси в
тунелі додайте в `--never-block`.

### 5.3 `MODE=DEGRADED`

| Метрика в `0` | Причина | Дія |
|---|---|---|
| `sokol_audit_healthy` | диск заповнений, права, збій запису | звільнити місце або виправити права; відновлюється само; healthy не означає повну історію; втрати — `AUDIT_LOST`/`AUDIT_QUEUE_OVERFLOW`, межі — AUDIT-R1/R2 і REPLAY-R5 |
| `sokol_state_healthy` | запис стану не вдається або висить > 5 с | див. `sokol_state_pending_seconds` і журнал `[State]`; відновлюється само |
| `sokol_state_restore_ok` | стан не відновився при старті | §5.4 |
| `sokol_protected_refresh_ok` | не читаються адреси хоста | журнал `[BlockPolicy]`; відновлюється само |

### 5.4 Стан не відновився при старті

У журналі — `[State] Restore failed: …; bytes kept at …`. Вузол працює, але без попередніх
власних рішень і знять. Байти збережено в `<state-file>.corrupt[.N]`.

1. Подивіться причину: пошкоджений файл, права або інша схема («state schema N, this build
   reads M»; міграцій немає, ADR-0004).
2. Якщо стан можна повернути, зупиніть службу, поверніть правильний файл на місце й запустіть.
3. Якщо ні, прийміть втрату. Бани оператора й зняття тоді треба відновити вручну.

```shell
ctl ACCEPT_STATE_LOSS             # "OK state loss accepted"; вузол виходить із DEGRADED
```

### 5.5 Пір не з'єднується

Шукайте в журналі обох вузлів:

| Запис | Причина | Дія |
|---|---|---|
| `Rejected envelope … UnknownSender` | ключа піра немає в `peers.json` | додати ключ і `ctl RELOAD_PEERS` |
| `Rejected envelope … BadSignature` | ключ у `peers.json` не той | звірити `--print-public-key` піра |
| `Rejected envelope … StaleTimestamp` | годинники розійшлися > 30 с | налаштувати chrony/NTP |
| `has only a legacy Dilithium3 key` | у `peers.json` старий ключ v1 | новий `mldsa65:` ключ піра (README, оновлення v1→v2) |
| `pre-versioned mesh protocol` / `no common mesh protocol version` | пір іншої версії | оновити пір |
| `no handshake within 5s` | з'єднання мовчить | мережа, файрвол (TCP 7946) |

Меш сходиться сам: дайджести кожні 15 с, знімок — не частіше разу на 5 с на піра.

### 5.6 Адаптер детектора не доставляє

- Журнал адаптера: `alerts queued, retrying` (Suricata) чи `decisions queued, retrying`
  (CrowdSec) означає, що вузол недоступний, а сигнали чекають у черзі (до 10 тис. для
  Suricata, 100 тис. для CrowdSec).
- Suricata з `--cursor-file` після рестарту продовжує з місця зупинки. Алерти, старші за
  10 хв, пропускає.
- `EVE line ... exceeds 1048576 bytes; skipping to LF`: запис більший за ліміт 1 MiB
  (разом із LF) навмисно пропускається, навіть якщо це коректний JSON. Перевірте обсяг
  полів у виході Suricata. `invalid UTF-8 EVE line` означає пропущений пошкоджений рядок.
  Ліміт циклу читання — 1 MiB байтів або 256 завершених рядків; це квота роботи, не дедлайн.
  Коли квоту вичерпано, доставка та перевірка потреби зберегти курсор (раз на секунду)
  виконуються перед наступним пакетом, але паузи 50 мс між такими пакетами немає.
- `--max-alert-age-secs`: неможливий для локального монотонного годинника інтервал
  завершує запуск з помилкою CLI (код 2), до читання EVE/курсора чи IPC. Виправте
  конфігурацію; це не значення «вимкнути перевірку». Нуль лишається допустимим,
  але timestamped-алерти пропускаються до прийняття політикою.
- `queued alerts expired before forwarding`: строк пересилання timestamped-алертів
  сплив під час черги, backoff чи handshake. Вони відкинуті з окремим лічильником,
  їхні позиції більше не тримають курсор. Це локальна втрата, не ACK і не відкликання
  блоку, який міг уже застосуватися до втрати відповіді. Перевірте доступність IPC;
  `--max-alert-age-secs` обмежує пересилання, не TTL застосованого блоку.
- `alerts skipped: source cooldown active`: повтори адрес, уже прийнятих політикою,
  пропущено. Cooldown лишається чинним навіть якщо перший алерт згодом прострочився
  в черзі без надсилання; свіжі алерти тієї самої адреси приглушуються до його завершення.
  Повідомлення буває і в нормальному режимі: лічильник охоплює всі повтори, а не лише
  відмови після прострочення. Зіставляйте його з окремим журналом expiry та станом IPC;
  воно саме не доводить доставку чи блокування.
- `alerts skipped: cooldown memory full (100000 addresses)`: кеш cooldown заповнено
  чинними адресами. Нові адреси пропущено, чинні записи не витісняються; після спливу
  cooldown місця звільняються. Це втрата пересилання, а не черга повторної доставки.
  Перевірте потік адрес і налаштований `--cooldown-secs`; ліміт частоти стосується
  прийняття в локальну політику, не IPC-повторів.
- `alerts skipped: policy rate limit reached`: вичерпано `--max-signals-per-sec`
  у поточному фіксованому односекундному вікні. Алерти пропущені, не поставлені в чергу,
  курсор може пройти повз них; нульове значення відкидає всі алерти, що дійшли до Gate.
  Це не відмова вузла чи помилка IPC. Причина рахується за першою невдалою перевіркою:
  cooldown, потім rate, потім місткість; один алерт не потрапляє у кілька категорій.
- Усі три попередження політики вище агрегують кількості між пакетами.
  Рішення друкувати звіти розділяє щонайменше секунда монотонного часу,
  по одному рядку на категорію. Повільний stderr може зблизити видимі рядки.
  Перевірка виконується і на порожніх/error-проходах, тож новий алерт для публікації
  накопичених кількостей не потрібен. Доставка чи планувальник можуть затримати журнал;
  непубліковані кількості губляться при втраті процесу, лічильники насичуються на `u64::MAX`.
  Фільтри рівня журналу можуть приховати звіт: базові лічильники сформованих звітів
  просуваються і при вимкненому WARN. Інші повідомлення цим обмеженням не охоплено;
  пропуски парсера, severity/SID/freshness-фільтрів та втрати outbox цими лічильниками
  не покриваються.
- CrowdSec `--max-signals-per-sec` має бути додатним `u32` (типово 200).
  Нуль тепер дає помилку CLI з кодом 2 до звернення до LAPI чи IPC; раніше він
  непомітно означав одну команду на секунду. `--poll-secs 0` лишається допустимим.
  Пауза після завершеної IPC-команди округлюється вгору до цілих наносекунд,
  щонайменше 1 нс; це запитаний інтервал, не квота команд у ковзному вікні.
  Для Suricata нульовий ліміт прийняття як і раніше означає пропуск усіх алертів у Gate.
- Відкликання детектора при нестачі місця для заявок/записів повертає
  `OK refused retraction state capacity`; аудит і метрика відкликань мають результат
  `refused`. Це не знятий блок: опори й маркери події лишаються незмінними. Після
  звільнення місця можна явно повторити той самий `RETRACT#id`; адаптер поточну
  відмову завершує й автоматично її не повторює.
- Повтори прийнятих подій безпечні: вузол відповідає `OK duplicate`.

### 5.7 FlowSpec: кількість правил є, свіжого читання немає

Зчитайте одну HTTP-відповідь `/metrics`: `sokol_flowspec_announced` містить
останню успішно спостережену кількість власних source-prefix правил у локальному RIB.
`sokol_flowspec_discard_rules` — їхня підмножина з перевіреною canonical discard дією.
Різниця означає власні шляхи з непідтвердженою дією; сама рівність чисел не доводить
збіг prefix із бажаним набором.

- `sokol_flowspec_enabled = 0`: worker вимкнений, у тому числі в observe mode;
  нульова кількість не є підтвердженням порожнього RIB.
- `sokol_flowspec_enabled = 1`, `sokol_flowspec_readback_ok = 0`: ще немає
  успішного раунду, раунд триває, читання/запис завершилися помилкою або задачу
  скасовано. Наявна кількість лишається попереднім спостереженням.
- `sokol_flowspec_readback_age_seconds = -1`: успішного спостереження ще не було.
  Інакше це монотонний вік від початку останнього успішного читання обох сімейств;
  він зростає і без нового основного tick, і після помилок.
- `sokol_flowspec_readback_ok = 1`: останній раунд завершився успішно.
  Перевірте також вік за допустимою для вашого споживача межею; універсального
  production-порога немає. Цей стан не доводить збіг бажаних і фактичних правил.
- `sokol_flowspec_round_converged = 1`: owned і canonical-discard prefix sets
  збіглися з wanted, зчитаним на початку останнього завершеного раунду. Зміна
  intent під час або після цього раунду може ще очікувати обробки; перевіряйте вік.
  `0` означає невідповідність або непідтверджений стан, включно з pending/failure.
  За health 1 і convergence 0 перевірте залишкові/відсутні правила та actions,
  квоту 64, policy GoBGP і reuse ownership-community/hidden ID. Нуль після
  вимкнення worker не доводить наявності розбіжності. Ця ознака не дає додаткових
  прав і не підтверджує latest intent, справжні path IDs чи upstream enforcement.

При тривалому невідомому стані перевірте доступність налаштованого GoBGP API,
частоту справжніх змін бажаного набору та
журнал `[Flowspec]` і обидва локальні RIB. `unreadable RIB` означає непридатне
читання: навіть exit 0 з порожнім stdout, `null` чи помилковими полями класифікації
не підтверджує порожній RIB. Закріплений CLI повертає `{}` для справді порожнього
RIB. Непридатне початкове читання зупиняє записи раунду; непридатне читання після
записів лишає їхній результат непідтвердженим, з попередніми counts/time і health 0.
Успішний наступний раунд відновлює
health і оновлює обидві кількості та час разом. Повідомлення `local FlowSpec path
collision` означає відому колізію з чужим локальним шляхом: пропущено тільки
конфліктні операції, решта відкликань і анонсів продовжується; health лишається 0. Узгодьте namespace або серіалізацію writers; різні communities не
захищають від запису на той самий NLRI. CLI не має атомарного compare-and-swap.
При shutdown власний шлях із колізією також не видаляється; він може лишитися
upstream після закінчення бюджету спроби. Перевірте та розв’яжіть ownership у gobgpd.
Це локальна перевірка canonical discard, не роботи upstream-маршрутизатора. Помилка HTTP або відсутність
серій також не є підтвердженням порожнього RIB.

Зміна wanted зберігає початкове й завершальне RIB read; після початкового
читання worker бере актуальний бажаний набір для плану. Перед кожною командою
перевіряється membership: add лише для ще бажаного prefix, delete лише для вже
небажаного. Зміни інших prefixes не перезапускають доречну pending команду.
Недоречна команда скасовується; наступний план потребує нового RIB read.
Завершений раунд порівнюється зі своїм sampled target; якщо актуальний набір уже
інший, наступний раунд починається одразу. Однакові публікації main tick не
повідомляють watch channel. Shutdown true або закриття intent/shutdown channel
перериває звичайний раунд і запускає cleanup із бюджетом 10 секунд; false
notification не скасовує поточну роботу.

Скасована команда може вже мати ефект у GoBGP. Нове читання спостерігає RIB для
наступного плану; це не rollback чи fence для remote RPC у польоті. Навіть
direct/exec CLI може лишити RPC, який застосовується після нового читання.
Cleanup може побачити порожній RIB до пізнього add і повернути успіх; це не
гарантує відсутності правил після виходу worker. Publication і CLI не атомарні.
Обгортка має використовувати `exec`: kill-on-drop завершує прямий child, не все
дерево процесів. Скасована local reply може не залишити ACK-аудиту прийнятої дії.
Збереження корисних futures знімає перезапуск від несуперечливих змін, але не
доводить eventual convergence при безперервній зміні того самого prefix.
Повільний/несправний CLI, ownership collisions і backlog можуть тримати health 0;
при негайному новому раунді успішні counts/time можуть оновитися з уже відкликаним
health. Квота 64 діє на раунд, не на сукупну частоту команд; cleanup лишається
обмеженою спробою withdrawal.

## 6. Ключі: ротація, відкликання, компрометація

- **Ротація без простою.**
  1. Згенеруйте новий ключ: `--key-file /var/lib/sokol/node.key.new --print-public-key`.
  2. На всіх пірах пропишіть обидва ключі: `"public_keys": ["<старий>", "<новий>"]`, потім
     `ctl RELOAD_PEERS`.
  3. Замініть `node.key` новим і перезапустіть вузол.
  4. Приберіть старий ключ з усіх `peers.json` і знову виконайте `RELOAD_PEERS`.
- **Відкликання вузла.** Приберіть його з `peers.json` на всіх вузлах і виконайте
  `ctl RELOAD_PEERS`. Його заявки перестають діяти одразу (`revoked`), з'єднання
  закривається на першому ж повідомленні.
- **Зіпсований `peers.json`.** Помилка синтаксису, помилка в ключі чи дублікат не міняють
  чинну довіру: відповідь `ERR …; previous trust store kept`.
- **Компрометація вузла.** Відкличте його (див. вище), потім перевірте аудит інших вузлів:
  `MESH_BLOCK_HELD` показує, що його заявки обмежував конверт чи кворум (ADR-0007).

## 7. Оновлення й відкат

Релізу ще немає, тож формати можуть змінюватися без сумісності; кожна зміна описана в ADR.

- Бінарник оновлюється як звичайно: встановити й `systemctl restart`. Перевірте
  `sokol_build_info`.
- **Відкат** — це бінарник, `node.key`, `peers.json` і файл стану **разом**. Файл стану іншої
  схеми не відновлюється (§5.4).
- Перехід протоколу мешу v1→v2 виконується в одне вікно на всіх вузлах; локальний захист
  при цьому працює (README).

## 8. Аварійно зняти фільтр

```shell
sudo systemctl stop sokol-orchestrator
ip -d link show eth0              # prog/xdp зник: трафік іде без фільтра
```

Smoke перевіряє, що зупинка служби (і навіть SIGKILL процесу) знімає XDP-програму з
інтерфейсу. Бани оператора збережені у файлі стану й повернуться при наступному старті.

## 9. Пілот: фаза 0 — тінь

```shell
SOKOL_ARGS=… --enforce observe      # у /etc/default/sokol, потім systemctl restart
```

- Вузол ухвалює всі рішення й пише аудит, але його рішення **ніде не відкидають
  пакетів** (ADR-0018). Власні заявки не йдуть у меш, FlowSpec не анонсується навіть із
  `--flowspec-gobgp`, телеметрія не заявляє атаку. Заявки пірів вузол приймає, але не
  відкидає за ними.
- Що він відкинув би, видно тут:
  - `metric sokol_xdp_observed_packets_total` — за причинами;
  - `sudo sokol-monitor --outcomes /var/lib/sokol/audit.log` — кожен блок: скільки відкинув
    би і чиє рішення. У тіні `Dropped:N` означає «відкинув би N».
- Режим видно в `metric sokol_enforce_mode` і в аудиті (`ENFORCE_MODE|Mode:observe`).
- Перехід до відкидання: `--enforce drop` і рестарт. Рішення, що діють, зберігаються.

## 10. Чи випливає рішення з того, що записано

```shell
sudo sokol-orchestrator --replay /var/lib/sokol/audit.log
```

Перевіряє ланцюжок і проганяє рішення детекторів тим самим кодом (ADR-0016):
- `N reproduced` — рішення відтворено;
- `MISMATCH` — рішення не випливає з записаних входів (з обома значеннями);
- `INSUFFICIENT` — бракує контексту, з причиною. Найчастіше це інша збірка або запуск,
  що відновив стан із файлу. Невідтворена відмова відкликання через місткість також
  неперевірена: replay не знає всіх заявок/власників з mesh і припиняє перевірку залежних
  рішень до нового придатного `NODE_START`. Це не підтверджує правильність відмови.
- `AUDIT GAP` — журнал явно повідомляє про втрату (`AUDIT_LOST` або
  `AUDIT_QUEUE_OVERFLOW`); залежні рішення не перевіряються до свіжого `NODE_START`.
  Маркери рахуються окремо від рішень. Навіть маркер наприкінці журналу робить його
  неповним; наступний успішний запуск не стирає пропуск. Відсутність маркерів не
  гарантує повноти запису: failed sync/reopen або зупинка до запису маркера можуть
  залишити втрату без повідомлення (REPLAY-R5). Завеликі записи та відомі втрати черги
  обліковуються перед наступним записом або sync, навіть без наступного Record.
  Успішний фінальний `flush` з маркером означає sync журналу, а не повну історію;
  після завершення producers перевіряйте і replay, і метрики втрат (AUDIT-R1/R2).
  Штатний shutdown тепер завершує producers і прийняті IPC/control handlers до
  фінального state snapshot та audit-бар’єра (SHUTDOWN-S1/S2). Застряглий ACK або
  клієнт, що не надсилає рядок, не лишає handler працювати після фінального flush.
  Уже застосоване рішення може лишитися без ACK; непідтверджені входи не вважаються
  відмовленими. Непрочитані входи не дренуються, SIGKILL/crash-повнота не гарантується.
  Незавершений blocking host discovery може затримати вихід runtime, але після
  зупинки його parent не змінює таблицю й не пише audit. Помилки фінального state
  write або audit fsync лишаються явними помилками, а не підтвердженням збереження.

Код виходу: 0 — є відтворені рішення без розбіжностей, `INSUFFICIENT` і пропусків; 1 — є
розбіжність; 2 — неповний результат, нічого не відтворено або ланцюжок не перевіряється.
Раніше змішаний неповний результат міг дати 0; агенти мають обробляти 2 як брак доказів.
Відмови захищеного набору рахуються окремо й не перевіряються навіть при коді 0.

Новий `DB_LOG` з сигнального сокета зберігається як `CLIENT_LOG|Message:...`:
це видимий у monitor текст, який не підставляє вузлу службові записи або рішення.
Старі неогороджені записи не мігруються; ланцюжок не засвідчує їх походження.

Запускайте той самий бінарник, що ухвалював рішення.

## 11. Пакет для підтримки

```shell
sudo CONTROL=/run/sokol/control.sock PEERS=/etc/sokol/peers.json scripts/support-bundle.sh
```

Створює `sokol-support-<час>.tar.gz` (`0600`). Усередині:
- система, версія й хеш бінарника;
- стан systemd і журнал;
- метрики, бани, перевірка аудиту;
- прив'язки XDP, стан BPF;
- піри (лише ID й тип ключа).

Ключа вузла й сирих файлів стану та аудиту там **немає**; smoke перевіряє, що байтів ключа
немає в жодному файлі пакета.

## Репетиція

```shell
sudo scripts/runbook-rehearsal.sh <тека зі збіркою> <тека з іншою збіркою>
```

Проганяє цей документ на чистому хості з systemd: команди — як написано вище, трафік — через
veth до мережевого простору імен (бан не відріже оператора). Друга збірка грає оновлення.
Кожне місце, де документ і програма розходяться, друкується як `RUNBOOK DEVIATION`.

Перевіряє: §1–§3 (зокрема кожен рядок таблиці перевірок, крім дашборда), §5.1, §5.4, §7, §8 і
пакет для підтримки. Не перевіряє: збірку з джерел, меш і ротацію ключів (§5.5, §6 — потрібні
інші вузли), адаптери детекторів (§5.6).
