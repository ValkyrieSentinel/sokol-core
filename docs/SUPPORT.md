# Профіль підтримки

**Стан:** 2026-09-27, Pilot / Active Testing. Релізу немає, тож цей профіль описує, **на чому
Sokol-Core перевірено**, а не гарантію. «Перевірено» означає, що автоматична перевірка проходить
на цьому середовищі й тепер. Решта — або очікування з обґрунтуванням, або «не перевірено».
Змінюйте документ разом із тим, що справді перевіряється.

## 1. Перевірено

Кожен прогін CI і кожен PR проходить збірку, модульні тести, clippy, XDP smoke (понад 130
живих перевірок у мережевих просторах імен на veth) і демо на 3 вузли. Секції Suricata, CrowdSec, GoBGP і WireGuard
у CI обов'язкові (`SMOKE_REQUIRE`): відсутній інструмент дає FAIL, а не тихий SKIP.

## 2. Очікується, але не перевірено

| Що | Чому очікується | Що зробити перед пілотом |

## 3. Не перевірено й не підтримується

- Робота довша за годину під навантаженням. Годинний soak на 20 вузлах пройшов, але пам'ять
  подій (до 65 536 ідентифікаторів або 24 год) за цей час межі не досягла, тож плато RSS не
  виміряне ([2026-09-27](measurements/2026-09-27-lab/README.md)).
- Меш понад 30 вузлів; неповний меш (заявки не ретранслюються).
- Мережеві карти без XDP-драйвера у режимі `native` (лише `generic`, повільніше).
- SELinux/AppArmor із власною політикою, контейнерні оркестратори.
- Годинники вузлів без синхронізації: `expires_ms` абсолютний, вікно конвертів ±30 с
  (ADR-0003). **NTP/chrony обов'язкові.**
- Змішаний меш версій протоколу (v1 і v2), відкат без відновлення ключа й стану разом
  (ADR-0010).

## 4. Вимоги до вузла

- Linux з XDP, systemd, root лише для встановлення (служба працює як `sokol`).
- Синхронізація часу (NTP/chrony).
- Файлова система для `/var/lib/sokol` з `fsync` і атомарним `rename` (ext4, xfs).
- **Пам'ять і потік подій залежать від кількості CPU** (N03). Вузол друкує на старті
  `[Resources] …` зі своїми значеннями:
  - лічильники влучань блоків: 1 МіБ × possible CPU (64 CPU → 64 МіБ), навіть якщо частина
    CPU простоює;
  - стеля подій: 64 × CPU на секунду; кільце на 256 КіБ вміщує ≈ 840 подій, тобто за
    64 CPU на стелі ≈ 0,2 с, якщо споживач зупинився (решта рахується як пропущена);
  - межа 64/с — у вікнах по секунді, тож на стику двох вікон можливі дві порції по 64.
- Для Flowspec — gobgpd, що має BGP-сесію з маршрутизатором; для мешу — TCP 7946 між усіма
  вузлами (бажано через WireGuard).

## 5. Як перевірити свій профіль

```shell
sudo scripts/xdp-smoke.sh target/release/orchestrator   # понад 130 живих перевірок
sudo DEMO_AUTO=1 demo/demo.sh target/release            # 3 вузли, зловмисник, чужий вузол
```

Якщо все зелене на вашому ядрі й архітектурі, додайте рядок у таблицю §1 разом із тим, як
саме перевіряли.

**Швидкодія на вашій мережевій карті** (`native`) — дві машини, з'єднані через цю карту:

```shell
sudo bench/nic.sh dut target/release/orchestrator <iface> native   # вузол під тестом
sudo bench/nic.sh gen <iface> <MAC вузла> <IP вузла> <pps> <секунд> # джерело трафіку (pktgen)
```

- Генератор шле 64-байтові кадри з `198.18.0.1–254`; вузол блокує `198.18.0.0/24` і щосекунди
  друкує відкинуті пакети/с та CPU (softirq і загальний).
- Піднімайте `pps`, доки відкинуте перестане дорівнювати надісланому (генератор друкує
  `sent`): це межа фільтра на цій карті й CPU.
- Затримку легітимного трафіку під навантаженням вимірюйте окремо: `ping -i 0.01` з
  незаблокованої адреси.
- `bench/nic.sh local` проганяє ту саму методику на одній машині через veth (native XDP)
  разом із ping. Цифри в цьому режимі не про карту: генератор ділить із вузлом CPU.
