# Sokol-Core: стан і наступні дії

Дата: 2026-10-11. Переглянутий commit: `4c6cc75631dd4d9341627172578d4d19410d8eb8`.
Git tree: `ef9babfedb6c5637fed34c0be61c7a157ed6c0ee`.
Це датоване рев'ю й рекомендований план, не новий нормативний контракт і не прийняття release.
Після зміни коду, CI або ruleset його спостереження треба перевірити заново.

## Висновок

Sokol має робоче ядро для керованого розподіленого виконання мережевих блокувань:
власників заявок, окремий бажаний і застосований стан, обмеження повноважень пірів,
відновлення, аудит, виконувані свідки й відмову від непідписаного послаблення контрактів.
Останні виправлення проходять не лише unit tests, а й живі XDP/GoBGP перевірки,
демо й репетицію оновлення та rollback на двох архітектурах.

Водночас лабораторна кваліфікація ще не встановлює production-придатність на фізичній NIC,
а підпис тесту ще не встановлює повноту його перевірки. Для більш самостійної роботи ШІ
наступна користь — закрити розриви між проголошеними й фактично обов'язковими gates,
обмежити вхід до виділення великих буферів і давати агентам контекст із перевіреними
результатами та явними невідомими.

## Що перевірено зараз

- Локальний `main` і GitHub `main` збігаються; відкритих PR немає. Дерево після merge
  збігається з деревом фінального, перевіреного head PR #8 (`56e6389`).
- [CI на поточному main](https://github.com/s0fractal/sokol-core/actions/runs/38097089077)
  успішний: x86_64/aarch64 tests, smoke, demo/rehearsal і Kani.
  [Delivery shadow](https://github.com/s0fractal/sokol-core/actions/runs/38097089152) також успішний.
- [CI фінального PR #8](https://github.com/s0fractal/sokol-core/actions/runs/38096467652)
  має успішні всі чотири mutation shards і їхній агрегатор. На push у `main` ці jobs
  пропускаються за задумом; це не новий sweep усього коду.
- Свіжий локальний `witness-pin.py check`: 40 підписаних рядків, 101 свідок.
  Є 41 JSON-контракт: `MESH-K1` поки не pinned. Наявний до рев'ю локальний намір
  `MESH-K1-87538f12083b.proposal.json` непідписаний і не прийнятий.
- Свіжий `scripts/check-delivery.sh`: 29 tests пройшли та socket probe завершився.
  `test_witness_pin.py`: 18; `test_contract_tool.py`: 13;
  `test_contract_shadow.py`: 14 — усе пройшло.
- Проєкція контракту перевіряє підпис відносно наданого signer-файлу й чесно залишає
  виконання `UNKNOWN`. `outbox-task.py` віддає обмежений пакет для IPC-A1, але сам
  підпис не перевіряє (`NOT_CHECKED`) і tests не запускає.

У цьому рев'ю прочитано поточні architecture/support/ADR/contract/CI поверхні й простежено
межі delivery, peer admission/reload, FlowSpec subprocess/readback та state restore.
Це не вичерпний незалежний аудит кожного runtime-шляху. Повний CI повторно не запускався:
для незміненого дерева є свіжий remote результат. Production-код, підписи й GitHub налаштування
під час цього рев'ю не змінювалися.

## Найважливіші прогалини

### R1 — P1: mutation і Kani не є обов'язковими merge checks

Живий ruleset `protect-main` (`24848666`, active, без bypass actors) вимагає лише
`build-test-smoke`, `build-test-smoke (arm64)` і `delivery`. Агрегатори архітектур
у `.github/workflows/ci.yml:371–391` залежать лише від `suite`, не від `kani` чи `mutants`.
Тому невдалий результат Kani або пропущений тестами мутант сам по собі не є бар'єром
злиття. Нинішній head зелений; знахідка стосується захисту наступних змін.

Рекомендація: зробити `kani` й агрегатор `mutants` обов'язковими checks або включити їх
у один обов'язковий gate. Перевірити випадки failed/cancelled/skipped/missing, щоб
незастосовна перевірка була явним scoped результатом, а зникла job не стала успіхом.
Зміна required checks сама по собі не додає нових обчислень: ці jobs вже запускаються.

### R2 — P2: таймаут GoBGP не обмежує байти відповіді

`GobgpCli::run`, `orchestrator/src/flowspec.rs:204–219`, використовує `.output()`:
stdout і stderr накопичуються повністю до перевірки статусу. `CALL_TIMEOUT=5s` обмежує
час, але не обсяг пам'яті чи діагностичного тексту. RIB потім розбирається без ліміту
вхідних байтів; він містить також правила, які Sokol не створював.

Ізольований Linux ARM64 пробник виконав актуальні `run` і `observed` з керованим
subprocess замість GoBGP. Префікс файла `flowspec.rs` незмінений; додано лише виклик
приватної функції для виміру довжини. Audit sink і форматування адрес — заглушки, які
цей шлях не використовує. Поточний Cargo.lock використано як початковий lock для
офлайн-збірки окремого, меншого dependency-набору.

Результат: 67 108 864 байти stdout прийнято; 67 108 864 байти stderr стали повідомленням
помилки; `{}` із 64 MiB пробілів прийнято як RIB для обох сімейств. Повторний прогін:
1 564 ms, peak RSS 140 416 KiB. Це доказ відсутності ліміту на цьому шляху, не
демонстрація віддаленого злому чи production OOM.

Рекомендація: окремі named bounds для RIB bytes і діагностики; одночасно читати обидва
pipe з межами; перевищення відмовляє observation, припиняє/reaps subprocess і не
дозволяє трактувати обрізану відповідь як порожній RIB. Межа має вміщувати найбільший
прийнятий профіль, з регресіями exact-limit/limit+1, stdout/stderr flood та retry.
Не встановлювати довільний малий ліміт, що зробить чинний великий RIB неперечитуваним.

### R3 — P2: restore обмежує таблиці після необмеженого читання

`state_store::read_state`, `orchestrator/src/state_store.rs:344–381`, спершу робить
`std::fs::read`, потім десеріалізує весь `Persisted`. Нові межі `BlockTable::restore`
захищають збережені runtime-таблиці, але не ці попередні буфери й колекції.
Це підтверджено читанням коду; окремого OOM-прогону не було. Доступ до state file
локальний, тому це насамперед відмовостійкість після пошкодження/помилки оператора.

Рекомендація: обмежити читання й десеріалізацію до або під час allocation;
показувати failed restore, зберігати вихідні байти й не перетворювати перевищення на
успішний fresh start. Обов'язково перевірити найбільший легальний snapshot і bounds
рядків/колекцій, а не лише розмір JSON-файла.

### R4 — P2: межі MESH-K1 треба уточнити перед підписом

Контракт містить сильне формулювання про неможливість відмови іншому піру через обсяг
одного піра. `adopt` одночасно має загальну межу peer claims і окремий `max_known`.
ADR-0025 чесно зазначає, що три стандартні частки заповнюють спільний peer budget;
допустимі конфігурації часток самі по собі не резервують незалежну пам'ять кожному піру.
Тому загальну гарантію fairness для довільного мешу/конфігурації не встановлено.

Рекомендація: окремо сформулювати per-peer bound, own reserve і умовну доступність для
іншого піра. Додати saturation/reload/revocation vectors для заявлених конфігурацій,
тоді запропонувати узгоджене формулювання й свідків. Наявний намір додає reload-свідків,
але зберігає старе формулювання. Прийняття й repin залишаються актом власника.

### R5 — P3: контекст агентів уже працює, але ще локальний і без результату виконання

`outbox-task.py` і `contract-shadow.py` прив'язані до IPC-A1. Хеші тіла свідка не
закріплюють його helpers/fixtures; ADR-0023 це явно визнає. Тому `MATCH` підписаних
байтів не є висновком про semantic adequacy. Ідентифікатори request/response також
не входять у нинішній ACK: перевірка тиші перед записом ловить вже наявні зайві
байти, але не встановлює криптографічну чи протокольну належність наступної відповіді
конкретній команді. Це межа протоколу; live-баг поточного node handler тут не відтворено.

Вже є маленький приклад дрейфу пояснення: генератор каже «the two witness bodies»
(`contract-shadow.py:99`), хоча IPC-A1 зараз має чотири свідки. Структурна перевірка
при цьому перевіряє всі чотири. Вступ ARCHITECTURE досі говорить про очікування merge
PR #36–42 і 166 tests; датована базова лінія ROADMAP також не є поточним inventory.

Рекомендація: поточні counts/status генерувати; пояснення лишати поясненнями;
додати загальний read-only task context і окремий перевірюваний execution report.
Не видавати підпис за доказ повноти й не вимагати owner repin для звичайної зміни
реалізації, яку чинні незмінні свідки приймають.

## План у порядку виконання

| Етап | Конкретний результат | Критерій завершення |
|---|---|---|
| 1. Обов'язкові gates і точні межі | R1; scope review MESH-K1; короткий поточний inventory | Required-check readback містить усі прийняті gates; failure/cancellation не дозволяє merge; MESH статус і конфігураційні межі явно видимі |
| 2. Ресурсні межі на входах | R2/R3 одним завершеним пакетом, якщо зміни лишаються оглядними | Assertion-red на старому коді; найбільший легальний input проходить; перевищення відмовляє без allocation понад прийняту межу, втрати вихідних байтів чи хибного healthy/empty результату |
| 3. Перевірювана задача для агента | Узагальнити наявні інструменти: `context <contract-id>` і явний verifier report | Для IPC, mesh і restore пакет має snapshot, trusted signers, config/bounds, дозволений scope змін, команди й невідомі; зміна input робить старий execution report stale; без виконання немає PASS |
| 4. Цільове рев'ю решти safety core | Restore/replay/shutdown/audit/adapters; опрацьовані небезпечні survivors | По кожній вибраній межі є semantic mutation або явне обґрунтування еквівалентності; helper/fixture послаблення видно окремо; потрібні справжні process/crash/restart сценарії |
| 5. Кваліфікація одного deployment-профілю | Native NIC + kernel/driver + синхронізований меш + довший soak + rollback | Власники визначили оператора й пороги SLO/RPO/RTO/false positive; виміри на цільовому залізі відповідають їм; спершу observe, enforcement лише за прийнятим рішенням |

Етап 3 використовує чинні контракти, signer-механізм і тести. Звіт виконання зберігає
окремо pin correspondence, фактичний результат verifier, scope/config і невідоме.
Для helper closure спершу достатньо явного списку файлів/fixtures з digest та перевіркою
їхнього руху; це ще не доведення повноти dependency closure. Перевіряльник звіту має
перечитувати ці входи. Людині той самий пакет показує: що виправлено, чим перевірено,
що лишається невідомим; хеші відкриваються за потреби.

Ціна CI оптимізується разом із цими етапами. На фінальному PR #8 suite тривала приблизно
3–6 хв на job, найдовший mutation shard — 10 хв 8 с; Kani scoped skip — 4 с.
На main Kani — 12 хв 13 с. Отже, цей PR стримували mutants, а не Kani.
Спершу виміряти cache/install/build/baseline час кожного shard; застосувати ранній
локальний preflight, virtual time для нестабільних тестів і лише потім перевіряти
вартість повторної збірки. Повторне використання artifact допустиме за тотожності
SHA/digest/config, а не лише назви файла. Scoped skip перевіряти контрприкладами
зміни залежності. Зменшення кількості перевірених архітектур не є обраною оптимізацією.

Не ставлю в цей цикл нового ML-детектора, gRPC rewrite, універсального статичного
аналізатора, Kubernetes-пакування чи повернення вилучених інтеграцій. Підставою їх
розглядати буде дефект підтримуваного контракту або виміряна потреба пілоту.

## Відтворення R2

На Linux із кешованими залежностями поточного Cargo.lock:

```sh
python3 docs/status/2026-10-11/probe_flowspec_output.py --repo /path/to/sokol-core
```

Скрипт відмовляє, якщо source/lock digest змінився, працює в тимчасовому каталозі й
не змінює репозиторій. Результат цього рев'ю — `flowspec-output-result.json`.
Це source-path probe, не запуск повного daemon або справжнього GoBGP.
