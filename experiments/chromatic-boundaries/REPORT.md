# Результат: кольори корисні як карта меж, не як доказ повноважень

Дата: 2026-09-27. Вивчений Sokol-Core: `88d96c2ee25a9cc390089e8630a590d14fbbf8e4`.
Локальний запуск Python, без production-змін, Linux/XDP-тестів і мережевих дій.

## Що отримали

**14 файлів, 14 успішних тестів.** Позитивний manifest портів прийнятий. Навмисні зміни
«policy отримує disk», «exporter отримує apply_block/kernel», «peer отримує trust-update
endpoint без change_trust» відхилені. Окрема перевірка запускає CLI на негативному manifest
і отримує exit 1, а не лише текст попередження.

Ці три контроли змінюють **декларації запропонованих портів**, а не production-виклики Rust.
Ще один контроль незалежно змінює source fixture: додає policy→I/O залежність, не змінюючи
manifest. Inventory виявляє шлях `policy → io` і сигнал disk. Це локальний self-test, не
незалежне зовнішнє рев’ю.

## Спостереження на реальному коді

| Місце | Що реально спостерігали | Інтерпретація |
|---|---|---|
| `block_policy.rs` | `getifaddrs`, читання `/proc`, logging та unsafe поруч із policy checks | Один файл об'єднує discovery середовища й перевірку вже наданих даних |
| `control.rs → block_table.rs` | Parser імпортує `parse_target`; цільовий модуль містить Aya | Файлова карта фарбує parser у kernel-сімейство; це не доказ виклику ядра з parser |
| `signal.rs → block_policy/block_table` | Аналогічна залежність від змішаних модулів | Рівень операцій має відділити parsing/check від discovery/enforcement |
| `main ↔ mesh_sync`, `main → flowspec → main`, `main → p2p → mesh_sync → main` | Залежності на root `SentinelDb` і root declarations | Компонента взаємної досяжності: `flowspec, main, mesh_sync, p2p`; не помилка Cargo |
| `metrics.rs` | Підтримані шаблони ефектів не знайдено | `unknown`, а не `proven pure`; `std::fmt::Write` не плутається з console I/O |

Точні рядки сигналів, шляхи залежностей і hashes збережено в [result.json](results/result.json).
Текстові висновки обмежені зафіксованими байтами, не майбутнім HEAD.

## Що це говорить про початкову ідею

1. **Колір файла надто грубий для чистоти.** `check_net(&self, net)` та
   `protect_host_addresses(&mut self)` мають різні зовнішні взаємодії, хоча живуть поруч.
   На наступному кроці варто описати ці дві операції окремо й перевірити їхні виклики.
2. **Транзитивне фарбування показує coupling, але завищує ефекти конкретної функції.**
   `control::parse` використовує helper; він не успадковує автоматично всі повноваження
   `block_table`. Автоматичний gate за цією картою дав би хибні заборони.
3. **RGB працює як компактна проєкція, а capability sets — як контракт.** У вибірці
   отримано 6 кольорів при 8 можливих. Додавання 256 рівнів на канал поки не вирішує
   жодного виявленого завдання. Різні ефекти мають однаковий колір, тому authorization
   не можна робити порівнянням кольорів.
4. **Масштаб зараз потрібен структурний:** файл → інтерфейс → операція. Fixed-point Q
   передчасний, доки немає вимірюваної числової осі. Union зберігає сигнали при зменшенні
   деталізації; середнє кольорів могло б приховати вузьку небезпечну операцію.
5. **Кольорові порти — найперспективніша частина.** Однакова схема повідомлення й дозволений
   disk effect не дають права змінити trust. Для цього потрібне окреме `change_trust`.
6. **Колір не гарантує DAG.** Поточна карта допускає однакові кольори й цикли; цикл
   обчислюється явно. Для DAG потрібен окремий строгий порядок на правильно вибраних
   архітектурних одиницях. Root-файл, який містить і composition, і audit service, є
   невдалим атомом такого порядку.

## Що має сенс перевірити далі

- Взяти три операції: `BlockPolicy::check_net`, `BlockPolicy::protect_host_addresses`,
  `control::parse`. Перевірити їхні фактичні call edges, зовнішні inputs та mutation boundaries.
- Оцінити невелике виділення pure target helpers із `block_table` і host discovery із
  `block_policy`. Виправданість визначати зменшенням coupling та простішими перевірками,
  а не бажанням зробити карту «чорнішою».
- Розглянути окремий audit-service interface замість залежності на root `SentinelDb`.
  Це пропозиція декомпозиції, не встановлений runtime-дефект.
- Обрати один справжній ingress→decision→apply шлях і зіставити запропонований port contract
  із runtime-перевіркою credentials/capabilities. Без цього manifest лишається моделлю.

**Рішення за результатом експерименту:** зберегти RGB як оглядову карту й розвивати типізовані
порти; відкласти Q та числову Alpha. Перш ніж робити production gate, перейти до перевірених
operation-level контрактів. Система не повинна вимагати «перефарбувати все у біле» лише через
те, що pure helper живе в одному файлі з effectful adapter.
